# Design

- Wants UI built from the existing design system rather than per-screen bespoke styles: reuse the established theme tokens (typography, colors, spacing, borders, field heights, icons, button styles) and shared/reusable components so every screen — forms, reports, lists, dialogs, states — looks consistent. Confidence: 0.6
- For icon assets, wants minimal, clean, flat vector icons on a 24×24 viewBox with a transparent background, stripped of unnecessary detail so they stay legible at small sizes, using only simple colors that match the app's modern theme. Confidence: 0.55
- Wants default/stock framework glyphs (e.g. plain Material icons) swapped out for custom-drawn "modern" icons across navigation surfaces, rather than left as the library defaults. Confidence: 0.55
- Wants field labels always visible inside the input box (a persistent label line above the value), never a placeholder-style label that disappears as soon as a value is typed or a date is picked. Confidence: 0.7
- Wants report tables kept to the user-facing data only: internal/identifier and grouping fields (product IDs, group ID/name, category, category ID, the product code) should not get columns of their own — fold them into an existing cell or drop them and let grouping stand as headings/summaries rather than as repeated columns. Confidence: 0.55
- Wants products labeled with both code and name — written "Code - Product Name" (plain hyphen) — rather than the bare product name, in search/picker results and in report tables alike (e.g. the Product Name column), falling back to just the name when there is no code; the code should be folded into that existing label rather than given a separate Code column (stated again for multiple reports, e.g. Product Profit and Loss: "no new column is needed for the Code"). Confidence: 0.75
- Wants dates shown to the user in day-first form with a short year (`dd/mm/yy`, e.g. `14/11/26`), not raw ISO/stored `yyyy-mm-dd` strings. Confidence: 0.5
- Results-first screen layout: a tall filter form must never squeeze the results table — the table should get the bulk of the height and show many rows. Confidence: 0.55
- Dislikes extra chrome between the user and the report: wants a collapsible "Filters ▼" header/toggle removed when whole-page scrolling already handles it, so opening a report shows the filter form directly with no fold/expand control. Confidence: 0.6
- Prefers whole-page scrolling on reports over separately-scrolling regions: the filter header/form and the results table should live in one scroll container so swiping up carries the filter form off the top and reveals many table rows, and the inner table must not scroll on its own (no nested/double scroll). This is expected consistently on every report screen, and the reference behaviour is whatever screen already does it best. Confidence: 0.65
- Prefers dark mode for the app's visuals — states it "looks better" — and wants a single theme applied consistently across a final set of screenshots rather than mixing light and dark. Confidence: 0.6
