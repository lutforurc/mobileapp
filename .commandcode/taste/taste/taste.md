# Taste
- Report only what was actually done or verified — never claim an action (an upload, a Console change, a build, a test) occurred unless it really did, never fabricate results, and explicitly mark unknowns/placeholders as items for the user to confirm instead of filling them in. Confidence: 0.75
- Wants the assigned work done now rather than deferred or merely offered: proceed with the task instead of asking/waiting on other sessions or replying with only an offer to continue, and if blocked report the exact blocker. Confidence: 0.7
- Leave changes local and pre-publication: do not commit, push, upload, or publish without being asked. Confidence: 0.6
- Treat demo/live accounts as production: operate strictly read-only (navigate, view screens, run read-only reports, capture screenshots) — no creating, submitting, editing, deleting, importing or approving records, and no changes to settings, subscriptions, users, permissions or notification read-state. Any write or account-deletion testing goes in an isolated local/staging environment with synthetic data, never against the live/demo branch. Confidence: 0.85
- Verify technical claims at the source rather than by proxy: read the repository's routes, controllers and config to establish what exists, instead of inferring from black-box probing (e.g. HTTP 404s), and note which revision/branch was inspected. Confidence: 0.7
- Avoid over-absolute framing ("X is the only solution"): assess and present the full set of supported alternatives with their trade-offs instead of committing to one. Confidence: 0.6
- Keep credentials and secrets out of source code, release/build configuration, screenshots, logs, and public listing copy, and never print, echo or log them in command output, scripts or reports; confine them to a dedicated access document and treat shared/demo credentials with the same care as production ones. Never ask the user to paste a password, OTP/2FA code, private signing key or service-account JSON into chat — do authentication credential entry in the browser window they control. Confidence: 0.7
- Never treat an existing database as a test environment: for write or deletion testing stand up a separate checkout/configuration and a brand-new empty database, never run tests or migrations against an existing (especially business) database, and never copy production records for it. Confidence: 0.7
- Present a design and get explicit approval before implementing irreversible or destructive operations (e.g. anything that deletes data); distinguish destroying a single user's account from destroying shared company books and don't conflate the two without confirmation. Confidence: 0.65
- Treat real business/third-party data (customer names, phone numbers, live financial figures, product catalogues) as publish-sensitive: reachability through a demo account is not permission to publish it, so quarantine such material from public deliverables and wait for explicit user confirmation before including it. Confidence: 0.6
- Reviews/investigation passes are expected to be strictly read-only: when asked to review commits or update understanding of a codebase, do not modify any code, and base conclusions on reading the actual diffs (tracing related commits and comparing against the current code) rather than commit messages alone. Confidence: 0.6
- Prefers the smallest safe change: a targeted, idempotent fix that reuses the project's existing conventions (e.g. a focused command plus the codebase's own helper) over running a heavy wholesale/batch routine, and expects existing data and behavior to be preserved rather than silently reshaped. Confidence: 0.55
- Scope fixes to the cause: when addressing errors, change only the code responsible for each error and leave the surrounding code untouched — no incidental refactors or cleanup. Confidence: 0.6
- Wants findings classified rather than reported flatly: separate confirmed defects from intentional behavior, stale comments and harmless cleanup — check a change's intended behavior (e.g. from its commit history) before calling it a defect — and return confirmed issues ranked by priority with user impact and proposed fixes. Confidence: 0.6
